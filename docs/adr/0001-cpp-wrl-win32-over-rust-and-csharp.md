# Host PaneDock in C++20 with WRL ComPtr on native Win32

The decisive risk in this product is the `IExplorerBrowser` COM host contract — the site object, `IServiceProvider` callbacks, PIDL lifetimes, view teardown ordering — not application logic, and not memory. C++ is the native language of the Windows Shell API: the SDK headers, the official samples and the body of community knowledge are all C++ and can be consulted directly, and `Microsoft::WRL::ComPtr` removes the manual `AddRef`/`Release` bookkeeping that is the usual argument against it. Two independent selection reviews (2026-08-20) reached this conclusion separately and both corrected the same error in the original reasoning: memory is governed by the Shell views, not by the language runtime. In a four-pane configuration the host process is 5–20 MB against 150–500 MB of Shell views, thumbnails and in-process third-party extensions, so the runtime is roughly 5–8% of the total. The accepted cost is that the non-COM parts of the codebase — layout math, session persistence — give up compile-time memory safety they could have had, mitigated by confining them to `core` where they are fully unit-tested.

## Considered options

- **C++20 + WRL + native Win32 (chosen).** Zero translation layers over the Shell API; official samples are directly applicable; `ComPtr` gives RAII over interface pointers. Chosen because the project's hard part is exactly the part where C++ has the most available prior art.
- **Rust + windows-rs.** The bindings exist and are Microsoft-maintained, and the runtime footprint matches C++. Rejected: no reference `ExplorerBrowser` host exists in the Rust ecosystem, so every site and callback contract would be re-derived from Win32 documentation; and Rust's safety guarantees do not apply where they are needed, since the COM host, callbacks, vtables and marshalling all sit in `unsafe` and COM's cyclic object graph fights the borrow checker. The user's initial preference for Rust rested on "more stable", which does not hold — the crash surface is `shell32` and third-party shell extensions, which no language choice removes.
- **C# / .NET 8 (WPF `HwndHost`, or pure Win32 P/Invoke).** This was the original handoff recommendation. Rejected on developer experience and long-term maintenance: the marshalling layer over the site contract, `IServiceProvider` callbacks and PIDL lifetimes is a maintenance liability, and NativeAOT would additionally forbid classic `ComImport` in favour of source-generated `ComWrappers`, raising interop cost further. Explicitly **not** rejected for memory — pure Win32 P/Invoke on CoreCLR lands at 20–60 MB resident, which is noise at this scale. The earlier claim that a 100 MB self-contained deployment implied unacceptable memory was a category error and is recorded as a rejected line of reasoning.
- **C++/WinRT.** Rejected: it improves WinRT API ergonomics and does nothing for classic `IExplorerBrowser`, adding an abstraction layer over the interfaces that matter.
- **Delphi / FreePascal.** Rejected: COM support is genuinely good and the footprint is low, but the ecosystem, available samples and maintenance outlook are far weaker for this specific API surface.
- **Zig.** Rejected: footprint comparable to C++, but COM integration would be entirely hand-rolled with no Shell host prior art, making it costlier than Rust.
- **C# UI shell + C++ shell-host DLL.** Rejected: the .NET runtime is still paid in-process so memory does not improve, while ABI, debugging and packaging complexity are added. This product's UI is a sidebar and five fixed layouts, so the work a C# shell could save is approximately zero. The one scenario that would justify revisiting a split architecture is out-of-process isolation of third-party shell extensions (`docs/design-spec.md` §14), which requires a recorded real-world extension crash first.
