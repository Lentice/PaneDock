## PD-224 implementation bounds (not performance measurements)

The local-folder slice enforces at most four process-wide live subscriptions/workers,
one replaceable pending request per subscription and two queued batches of at
most 128 rows each. A separate reserve of four retired workers (see below) has no
pending request or queued batch, so at most eight enumeration threads exist.
A worker, live or retired, may additionally hold one batch under construction;
UI consumption drains at most two batches before returning to input dispatch.
Requests cap each location string at 32,760 characters, each Group/tab id at 256
bytes, and item names at 255 characters. This enumeration slice has no property
cache; PD-229 adds the bounded icon path described below.
These value bounds keep queued results below the 16 MiB target; actual process
memory and allocator overhead still require the release measurements above.

Each Pane retains at most 100,000 rows and 24 MiB of row-vector capacity plus
owned name-string capacity (including terminators). Four live slots therefore have a
96 MiB accounted row ceiling, leaving headroom within the 128 MiB snapshot target
for identities and allocator overhead. Rebinding, derealizing and destruction
release rows; this slice does not retain inactive-tab lists. Exceeding either
row or accounted-byte bound stops interest and displays a visible limit state.
These bounds are implementation choices, not a measured PASS for the budgets.

Workers own only request/result values, their waitable event and their directory
read handle; they have no HWND, Pane/AppState or COM pointer. Cancellation clears
the pending request/results and invalidates the worker serial. Destruction signals
stop without joining an OS call. A stuck abandoned worker retains a bounded entry
and owned resources until it returns or the process exits; it cannot deliver to a
destroyed UI or create unlimited replacements. PD-226 changes successor admission:
a new destination reuses an idle worker or abandons the obsolete read and acquires a
free live slot. Because each Pane keeps its subscription for its lifetime, four
realized Panes hold all four live slots; an abandoned (retiring or destroyed) worker
that is still running or watching therefore moves into a separate four-entry
retired reserve, freeing its live slot for the successor at once. If the reserve is
full, the retiree stays in its live slot (the earlier behavior). Live and reserve
both occupied means immediate recoverable `Worker capacity exhausted` error, not
loading indefinitely behind an old call; at most eight enumeration threads exist.
Refresh is an explicit bounded retry; no automatic retry or polling timer is added.
Cancellation attempts `CancelSynchronousIo` on an owned thread handle without waiting;
unsupported/racing cancellation retains the entry until the old call exits. This does
not promise that Windows/provider calls can always be interrupted. The live/retired
split is an implementation bound; its effect on process memory and thread count
under a real slow provider is unmeasured.

## New-folder notification lag (implementation bounds, not measurements)

New-folder notification lag (2026-10-29): each Pane retains at most 16 pending
successful-creation records, each with one navigation binding, parsing name,
leaf name and creation sequence. Both names are limited to `kMaxPath` characters.
The entry vector reserves at most 16 slots; matched records release their
strings, and explicit sort or navigation/Refresh clears all pending records.
When all slots are occupied, creation is rejected before the next Shell call
and the status bar asks the user to wait or Refresh. There is no polling or
new worker. These are implementation bounds, not measured desktop evidence.

## PD-243 identity accounting (implementation bounds, not measurements)

The 24 MiB active-row budget includes Row-vector capacity and the capacities
(including terminators) of display text, stable item keys, optional absolute child
parsing name / known-folder identity / fallback path, and property text. Empty
strings are conservatively counted too. Each key/child component is at most
32,760 characters; local leaf keys and display text remain capped at 255.
The recovery index still stores row indexes rather than copied keys and retains
its separate 4 MiB allocator ceiling. Growth reserves headroom for owned strings,
so larger Row values do not spend all remaining budget on unused vector slots.

Inactive snapshots retain the existing 32 MiB global LRU budget. Their accounting
includes these same row strings, binding/location strings, selected-key vector
capacity and every copied focus/selection/viewport anchor key. Transient interaction
copies contain only keys from the bounded active snapshot plus three anchors;
no extra child-location copies, COM pointers or PIDLs are retained there.
PD-261 also admits completed/empty active-tab snapshots on Group rebind into
this same LRU. Returning to the exact Group/tab/full location shows Updating
immediately and refreshes with a new generation; inactive Groups retain no
source/watch or icon/property interest. Unbind, hidden-pane teardown and shutdown
discard that Pane's owner entries. These are memory-only values, never persisted.
The local worker/queue limits are unchanged; no namespace producer is enabled.
Capacity failures stop interest and remain explicitly retryable. These are value
and admission checks, not evidence of process memory or the PD-241 release gate.

## PD-244 enrichment identity accounting (implementation bounds, not measurements)

Icon-interest/request values are capped at 1 MiB per replacement window, in
addition to the existing item-count and worker/pending/result limits. The icon
cache's existing 4 MiB ceiling now accounts for each cached raster, cache entry,
and owned location/item identity capacities, including optional child parsing,
known-folder and fallback strings. Least-recently-used entries are evicted to
admit the next image; if one key cannot fit with the placeholders, it remains a
placeholder until a later explicit demand. These owned-value checks do not measure
GDI/provider memory or prove real Shell namespace compatibility.

`tests/release/release_evidence.ps1` regenerates `docs/release-evidence.md`. The contract is fail-closed:

- An unmeasured blocking metric produces **INCOMPLETE** and exit code 2. Absence of evidence is never treated as absence of a problem.

- A skipped test is not evidence. Skipped `ctest` results are reported as INCOMPLETE, not as a pass.
- Process totals and estimates are context only and never satisfy a gate.

## Why the language runtime is not on this table

An earlier selection review reasoned about memory by comparing language runtimes, and reached a wrong conclusion (recorded in `docs/tickets.md` §計畫決策紀錄, 2026-08-20). The correction, and the reason no runtime row appears above:

In the four-pane configuration the native host process is roughly 5–20 MB while the four Shell views plus thumbnails plus in-process third-party extensions are 150–500 MB. The runtime is about 5–8% of the total. Choosing a language to save runtime memory buys a rounding error and pays for it in integration risk.

For the legacy implementation, the decisions that bound memory are architectural and are stated in `docs/design-spec.md` §NFR-002:

1. Only the visible pane's active tab holds a live `IExplorerBrowser`.
2. The thumbnail pipeline has explicit cache and size caps.
3. Third-party shell extensions load lazily.

For the managed-list implementation, use the explicit acceptance budgets above and measure them on the defined corpus. Reasoning from deployment size, runtime baselines or another project's figures is not evidence here.

## PD-229 icon bounds (implementation limits, not desktop measurements)

Icon enrichment has four process-wide slots **in addition to** the enumeration
workers (four live plus four retired): at most twelve managed-list workers,
including abandoned calls. The separate capacity prevents slow EXE/LNK/overlay providers
from blocking first operable enumeration batches. Each icon slot owns its STA,
one provider call, at most 128 replaceable pending requests and two queued
results (plus one result under construction). Queued inputs and identity keys use
the enumeration limits of 32,760 characters per location component, 255 per leaf,
and 256 bytes per Group/tab id. No worker owns a window or UI COM object.

Each Pane owns at most 128 visible identities of interest, zero offscreen
prefetch and 256 LRU cached images plus two local placeholders. Excess visible
rows retain placeholders until scrolling brings them within the interest window.
Raster dimensions are 16–64 pixels, selected from DPI; every returned raster is
validated as exactly size² 32-bit pixels plus a WORD-aligned 1-bit mask. The
maximum accounted color/mask payload is 4,359,168 bytes per Pane (258 × 16,896),
17,436,672 bytes across four Panes; the worker boundary holds at most another
202,752 raster bytes (four × three × 16,896). These are raster payload bounds,
not process/private-byte measurements or a claim about comctl32/Shell overhead.
Key strings, request values, allocator/GDI overhead and provider-owned caches
still require the existing full-process gate measurement. No thumbnails are
introduced here.

Navigation, Group/tab rebinding, hiding and derealization cancel queued interest;
a running provider may finish later but cannot update a different identity or
viewport generation. Cached identities include location, leaf name, size, modified
time, directory flag and raster dimensions. Eviction replaces an existing image
slot. Failure remains a placeholder and retries on renewed viewport interest or
Refresh, without a timer. An exhausted icon pool degrades to placeholders until
an explicit viewport/navigation retry. Destruction never joins a provider call;
its bounded slot/resources remain owned until the worker returns and tears down
its apartment. Cache refresh on external file changes belongs to the later change
notification slices.

The focused controlled test checks progressive operable rows while icons wait,
stale viewport/tab results, failure/retry, identity reuse/version changes,
eviction, DPI raster replacement, GDI cleanup, queue backpressure, saturation and
non-joining destruction. **No GUI or real-machine verification was run for this
ticket at the user's request.** Native EXE/LNK/overlay compatibility, mixed-DPI
rendering, OneDrive/virtual items, process memory/handles and ten-minute idle
CPU/I/O/wakeups remain **Not measured**, and are required by PD-241.

## PD-239 native context-menu latency comparison (2026-10-21; exploratory)

One normal-mode Release build (`E630EAC2325DFBE6896BC05B49D41B72887D2E95E3F8C4605398320694E23586`), one isolated local 33-byte `.txt`, and equal Medium-integrity PaneDock / File Explorer processes. A high-resolution stopwatch measured input release or F10 key-up to first visible classic `#32768` menu. Order was PaneDock → Explorer → PaneDock → Explorer; each menu closed with Escape. These are one first-per-process and one repeated sample per app, not a controlled cold-cache benchmark:

| App / sample | Latency | Menu items | Input |
|---|---:|---:|---|
| PaneDock, first | 1,659.0 ms | 25 | Selected-row real right-click |
| Explorer, first | 1,811.5 ms | 32 | Selected-row Shift+F10 classic Shell menu |
| PaneDock, repeated | 544.8 ms | 26 | Selected-row real right-click |
| Explorer, repeated | 353.9 ms | 33 | Selected-row Shift+F10 classic Shell menu |

Both first samples were in the same approximate 1.7–1.8 s range and both repeated samples were below 0.6 s. The same installed extensions (including 7-Zip, TortoiseGit, Notepad++ and klogg) appeared in both menus. This is consistent with shared Shell/extension enumeration cost, but four single-environment samples cannot establish attribution or a general performance comparison. PaneDock's warm row menu omitted Explorer's `IObit Unlocker` and `Rename` entries; Explorer's background classic menu also included view/sort/group/refresh and folder-view commands absent from PaneDock's managed-list menu. These differences remain compatibility observations, not an authorization for a custom menu.

Raw timing/menu output and screenshots: ignored `build\manual-test\pd239-latency\run-261021165715`; background menu comparison: `build\manual-test\pd239-compare\run-261021164904`. The release gate has no context-menu latency threshold; no managed-list or Windows Shell performance PASS is inferred.
